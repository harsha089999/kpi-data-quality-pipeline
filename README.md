# KPI Data Quality Pipeline

[![Run project](https://github.com/harsha089999/kpi-data-quality-pipeline/actions/workflows/run.yml/badge.svg)](https://github.com/harsha089999/kpi-data-quality-pipeline/actions/workflows/run.yml)

**A small raw, staging and marts pipeline in DuckDB with data quality gates that stop bad numbers reaching the dashboard.**

> **About the data:** everything in this repo is simulated, generated by the code with a fixed random seed so results are reproducible. The numbers describe the simulation, not the real world. Each project says how to swap in a real dataset.

## The business question

Can we trust this morning's KPI dashboard, and would we know automatically if the numbers were wrong?

## What this project does

Most dashboard problems are bad data nobody caught: duplicate loads, missing days, null keys, a sudden drop that is really a failed extract. This project builds a layered SQL pipeline with automated checks and only publishes the KPI table from clean rows.

## The data

Simulated daily order extracts from 1 September to 15 October 2026, about 400 orders a day across 4 stores and 2 channels, with deliberate faults: 20 September missing; 8 October has only 180 rows (a partial extract); on 2 October 6 rows have a null store ID and 3 rows have a dirty channel value ('Online '); and 12 October was loaded twice.

## How it works

1. Load the raw extract into DuckDB unchanged (`raw_orders`).
2. Staging (`stg_orders`): `SELECT DISTINCT` removes exact duplicate loads, types are cast and the channel is trimmed and lower-cased.
3. Run SQL checks that each return a count of failing rows: unique order IDs, no null store IDs, accepted channel values (all critical); no missing days and no day under 60% of the trailing 7-day average (both warnings).
4. Write the check results to a report.
5. Build the daily KPI table (orders, revenue, average order value) from rows with a store and a valid channel, so bad rows are left out rather than whole days dropped.
6. With `--strict`, exit with a non-zero code if any critical check fails so a scheduler or CI job fails.

## Run it

```bash
git clone https://github.com/harsha089999/kpi-data-quality-pipeline
cd kpi-data-quality-pipeline
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python src/main.py
```

It runs in about 15 seconds or less on a laptop and writes its files to `outputs/`. Python 3.10 or newer is recommended.

Add `--strict` (`python src/main.py --strict`) to make the run exit with an error when a critical check fails, as a scheduled job would.

## Results from the included run

This is the actual console output when the script is run as shipped:

```text
check severity  failing_rows status
  unique_order_id critical             0   pass
not_null_store_id critical             6   fail
 accepted_channel critical             0   pass
  no_missing_days     warn             1   fail
row_count_anomaly     warn             1   fail

CRITICAL checks failed: ['not_null_store_id']. Do not publish.
```

The duplicate load and the dirty channel values are fixed by staging (those checks pass). The 6 null store IDs fail a critical check, and the missing day and partial day raise warnings. The demo finishes with 'CRITICAL checks failed' on purpose, because the data is broken on purpose. Warnings do not block publishing in this design, so the partial 8 October day still appears in the KPI table. Whether warnings should block is a decision for the team.

## Output files

| File | What it contains |
|---|---|
| `outputs/dq_report.csv` | Each check with severity, failing rows and pass/fail status. |
| `outputs/kpi_daily.csv` | Daily orders, revenue and average order value from clean rows. |

## Limitations and honest caveats

- The checks are hand-written SQL. dbt tests or Great Expectations are the production equivalents.
- The database is in memory and nothing persists except the CSVs.
- No alerting beyond the exit code.
- The row-count rule is simple and will misfire on genuinely quiet days.

## Using real data

Replace `make_raw()` with a read of your real extract (for example `read_csv`), adjust the column names in `stg_orders` and add checks for your own business rules.

## Turning it into a dashboard

A 'data health' page showing each check's status over time, next to the KPI page it protects.

## Ideas to extend it

- Rebuild the checks in dbt and run `dbt test`.
- Send the report to Teams or Slack.
